# App Roles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a coarse system-access role to each user, stored in `timesheet_shorebase` rather than Supabase's `auth.users` metadata.

**Architecture:** One new SQL migration: a small lookup table (`app_role`, matching the existing `staff_type`/`room_type` pattern) seeded with three roles, plus a `role_code` column on the existing `app_user` table defaulting to the least-privileged role.

**Tech Stack:** Plain SQL migration under `supabase/migrations/`, applied via the Supabase CLI against the self-hosted Postgres connection string (same pattern as the existing `20260807000000_init_schema.sql`).

## Global Constraints

- Schema-only — no app code changes, no UI changes.
- One role per user (no junction table).
- Role is a separate, orthogonal concept from `job_position`/`user_position`/`approval_workflow_stage` — do not touch those tables.
- `role_code` must default to `'manager'` (not nullable, no default of `NULL`) so the existing `handle_new_auth_user` trigger needs no changes.
- Three seed roles: `master` (Master), `admin` (Admin), `manager` (Manager) — exact codes and names as given, lowercase codes.
- No automated tests for this pass (consistent with the rest of the project) — verification is running the migration against the real self-hosted instance and checking the result with `psql`.
- The one-off backfill statement for the project owner's own pre-trigger account is NOT part of the migration file — it's a separate manual statement the project owner runs themselves in Supabase Studio's SQL editor, since it touches `auth.users` directly (the assistant is blocked from querying `auth.users`, and it needs an email address that shouldn't be typed into the assistant's context).

### Task 1: Add `app_role` table and `app_user.role_code`

**Files:**
- Create: `supabase/migrations/20260810000000_add_app_role.sql`

**Interfaces:**
- Consumes: nothing — this is a new, self-contained migration on top of the existing schema in `supabase/migrations/20260807000000_init_schema.sql`.
- Produces: `timesheet_shorebase.app_role(code, name)`, three seed rows, and `timesheet_shorebase.app_user.role_code` (not null, default `'manager'`, FK to `app_role.code`). No other task in this plan depends on this.

- [ ] **Step 1: Write the migration**

Create `supabase/migrations/20260810000000_add_app_role.sql`:

```sql
-- Adds a coarse system-access role per user, stored in this schema rather
-- than Supabase's auth.users metadata. Separate from job_position/
-- user_position, which continue to drive business approval routing.

begin;

create table if not exists timesheet_shorebase.app_role (
  code varchar(32) primary key,
  name varchar(255) not null
);

insert into timesheet_shorebase.app_role (code, name) values
  ('master', 'Master'),
  ('admin', 'Admin'),
  ('manager', 'Manager')
on conflict (code) do nothing;

alter table timesheet_shorebase.app_user
  add column if not exists role_code varchar(32) not null default 'manager';

alter table timesheet_shorebase.app_user
  add constraint fk_app_user_role_code
  foreign key (role_code) references timesheet_shorebase.app_role (code);

commit;
```

- [ ] **Step 2: Apply the migration**

Run (sourcing `DATABASE_URL` from `.env.local` — never print or type the raw connection string):

```bash
source <(grep '^DATABASE_URL=' .env.local | sed 's/^/export /')
npx supabase db push --db-url "$DATABASE_URL"
```

Expected: the CLI reports the new migration applied, no errors.

- [ ] **Step 3: Verify against the real database**

Run (same sourced `DATABASE_URL`, still never printed):

```bash
psql "$DATABASE_URL" -c "select code, name from timesheet_shorebase.app_role order by code;"
psql "$DATABASE_URL" -c "\d timesheet_shorebase.app_user"
```

Expected:
- First query returns exactly three rows: `admin`/`Admin`, `manager`/`Manager`, `master`/`Master`.
- Second query's output includes a `role_code` column (`character varying(32)`, not null, default `'manager'::character varying`) and a `fk_app_user_role_code` foreign-key constraint in the "Foreign-key constraints" section.

Do not query `auth.users` at any point in this verification — it's out of scope and has previously been blocked by the environment's permission policy.

- [ ] **Step 4: Commit**

```bash
git add supabase/migrations/20260810000000_add_app_role.sql
git commit -m "Add app_role table and app_user.role_code"
```
